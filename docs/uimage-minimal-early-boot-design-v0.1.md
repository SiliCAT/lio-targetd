# uImage最小早期启动环境优化设计

版本：v0.1（原理性构思与概念设计）  
记录日期：2026-10-19  
对象：PogoPlug V4 / OpenWrt 25.12.0 / Linux 6.12.71  
定位：低优先级、独立开展的后续优化实验。本文不提供实现代码、构建命令或已经完成优化的结论。

## 1．设计结论与项目位置

现有启动链已经证明：内核先运行内嵌 initramfs 中的 sd-init，再运行 FAT 分区中的 init 脚本，可以完成 SD 分区识别、loop 文件镜像挂载、F2FS 与 overlay 组装，最终交接给正式 OpenWrt。

因此，内嵌 initramfs 可以从“完整 OpenWrt 根目录”缩减为“完成交接之前所需的启动工具、模块、动态库及 sd-init”。正式 OpenWrt 仍保留在独立的完整 SquashFS 镜像中。

优化后的部署形态仍是两个镜像：一个包含内核、DTB 和精简 initramfs 的 uImage；一个包含正式系统的 SquashFS。UBOOT 仍只加载一个 uImage，不增加独立 uInitrd，不改变现有业务层启动协议。

本项目目前的优先级安排是：先实现并验证 GitHub 工作流的干净构建，再以已经成功的完整 initramfs 为对照，单独开展本优化。本文不要求修改当前两个最小配置片段，也不把精简环境作为现阶段自动构建的前置条件。

## 2．现有基础与证据边界

### 2.1 已经成功的基础

| 项目 | 当前状态 |
|---|---|
| 硬件 | PogoPlug V4，ARMv5TE，128 MiB RAM |
| 构建方式 | amd64 构建机上的完整 OpenWrt 源码构建 |
| 早期镜像 | initramfs-uImage，约 7 MiB；内嵌完整根目录 |
| 正式只读系统 | FAT 上的独立 SquashFS 文件，约 4 MiB |
| 早期入口 | 内核参数 rdinit=/sbin/sd-init，sd-init 作为 PID 1 运行 |
| 可编辑业务入口 | FAT 分区内的 /boot/init |
| 存储布局 | BOOT：FAT32、只读；OVERLAY：F2FS、可写 |
| 正式根目录 | loop 上的只读 SquashFS 加 F2FS 上的 upper/work |
| 最终管理进程 | switch_root 之后由正式 OpenWrt 的 procd 管理 |

当前两个镜像的根目录内容大量重复，是因为构建时都使用完整的 root-kirkwood 根目录作为来源。最初这样做有利于先验证启动链：所需工具和模块已经齐备，不必同时排查裁剪缺失。

### 2.2 本文没有宣称完成的事项

精简 initramfs 尚未制作，也没有实机启动、内存对比或启动耗时对比结果。已有成功记录证明的是完整环境下的启动方案可行，不能直接算作精简方案验证通过。

LIO 核心、iblock 和 iSCSI target 已编入内核，但本轮没有完成实际 LUN 服务验证。精简早期环境也不代替这项业务验证。

## 3．优化对象和保持不变的接口

优化对象是“正式根目录接管之前，必须预先放在 RAM 中的文件集合”。

以下接口继续沿用：

- UBOOT 从 FAT 的 /openwrt/ 读取 uImage，继续使用已有内核加载方式。
- 内核先执行 /sbin/sd-init，保持 PID 1 的连续交接。
- 启动分区身份为 LABEL=BOOT，数据分区身份为 LABEL=OVERLAY。
- FAT 正常启动时只读挂载，根镜像通过只读 loop 读取。
- FAT 上的 /boot/init 保持可编辑，不因普通业务脚本调整而要求重新编译内核。
- 新空 upper 可以启动；已有 upper 正常保留，不以历史手工修订作为必备条件。
- mount_root 包装脚本仍由组装阶段生成，并保留向 /rom/sbin/mount_root 转发的设计。
- 交接时处理早期虚拟文件系统，由正式 OpenWrt 建立自己的运行环境，避免重复叠加。

本专项不同时调整内核驱动的内建/模块划分，不改 LIO 功能，不改正式 SquashFS 的业务包集合，不改变 SD 分区布局，也不加入版本选择或在线升级流程。

## 4．两个运行环境的职责分开

### 4.1 精简早期环境：负责找到并接入正式系统

内核展开 initramfs 后，早期环境只承担以下职责：提供 shell 和启动工具，识别 SD 分区，加载必需模块，读取 FAT 上的业务脚本，组装正式根目录，检查交接条件，最后执行 switch_root。

发生错误时，它还需要保留串口诊断与修复 shell，使 PID 1 不因脚本返回而退出。

### 4.2 正式 SquashFS：负责运行完整 OpenWrt

正式 SquashFS 继续包含 OpenWrt init、procd、preinit、原版 mount_root、正式软件包及其依赖、网络服务和业务工具。可写修改继续由 F2FS 上的 overlay upper 承担。

LVM 与后续 LIO 用户态配置工作属于正式系统阶段；当前早期组装业务并不需要先激活 LVM 才能读取根目录。因此没有必要仅因正式系统安装了 lvm2，就把它复制到精简 initramfs。

### 4.3 两份环境仍会有少量重复

BusyBox、musl、部分模块等可能同时存在于早期环境和正式 SquashFS 中。这是合理的：挂载正式根目录之前，早期环境必须能够独立运行；交接以后，正式系统也必须具备自己的运行工具。

优化目标是减少不必要的提前装入，而不是消除所有重复文件。

## 5．最重要的依赖边界：必须覆盖两层脚本

精简范围不能只根据 sd-init 的内容确定。FAT 上的 /boot/init 虽然存储在 SD 卡中，但执行它的 shell、它调用的工具和它加载的模块，在交接之前仍来自早期环境。

因此，早期文件集合必须覆盖以下三类需求：

| 需求来源 | 必须考虑的内容 |
|---|---|
| sd-init | shell、虚拟文件系统、设备节点、MMC/FAT 模块、LABEL 识别和失败处理 |
| FAT init | loop、F2FS、overlay 组装、内容比较、文件属性核对、包装脚本生成及根目录交接 |
| 串口修复 | 查看文件与挂载状态、加载模块、重新检查设备等基本诊断能力 |

如果只保留 sd-init 的依赖，系统可能可以挂载 BOOT，却在执行 FAT init 时才遇到命令、模块或动态库缺失，形成新的启动中断点。

## 6．精简环境的概念性组成

### 6.1 启动入口与基本目录

保留 /sbin/sd-init、/bin/sh、BusyBox，以及脚本使用的命令入口。准备早期运行需要的目录，包括 /proc、/sys、/dev、/boot、/mnt、/tmp 和新根目录挂载位置。

归档还需正确表达文件权限、所有者、符号链接和最初的控制台节点。不能只复制普通文件，而忽略 /bin/sh 的链接目标或动态加载器的真实文件。

无需预先复制 /proc、/sys 的运行时内容；它们由启动流程挂载得到。

### 6.2 命令与 BusyBox

第一轮建议复用当前成功构建中的 BusyBox 二进制，只筛选需要的命令入口。复用现有二进制可减少变量，但删除 applet 符号链接并不会移除已经编入 BusyBox 的功能代码。

因此，第一轮主要节省来自“少装其他文件”，而不是重新定制 BusyBox。若将来还有明显优化空间，再单独研究专用 BusyBox 配置。

命令能力应以两个现有脚本的实际使用为依据，覆盖挂载、模块装载、文件比较与属性检查、设备节点创建、超时等待、chroot 检查和 switch_root。

已知 cmp、stat、格式化 stat 输出、chroot、switch_root 是需要关注的实际功能。此前 BusyBox 的 --list 不可用，不能把这种枚举方式作为唯一的功能验收方法。

### 6.3 blkid、losetup 与动态库

当前成功镜像使用独立的 blkid 和 losetup，实际安装在 /usr/sbin。它们是 ARM musl 动态链接程序，不能只复制两个可执行文件。

精简环境应同时具备它们及 BusyBox 实际需要的动态加载器、直接共享库、共享库的传递依赖和相应链接目标。依赖集合应从本轮实际生成的 ARM 程序确定，不能从 amd64 构建机的运行库推测。

概念上采用“指定必需程序，再自动收集依赖”的方式。第一轮保留现有工具选型，不同时切换成静态程序或重新实现 LABEL/loop 功能。

### 6.4 内核模块与依赖

早期需要的模块分为以下功能组：

| 功能组 | 当前已经使用的代表模块 |
|---|---|
| SD 卡访问 | mmc_core、mmc_block、mvsdio |
| FAT 与字符集 | fat、vfat、nls_cp437、nls_iso8859-1，以及实际需要的 nls_base |
| 文件镜像块设备 | loop |
| F2FS 数据分区 | f2fs、当前装载链使用的 crc32_generic，以及实际依赖 |

这张表说明功能范围，不是可以直接用于打包的最终模块清单。最终集合必须根据相同内核构建产物核对，包含传递依赖；已经内建的功能不需要另找对应 .ko。

现有脚本使用 insmod 并明确安排装载顺序。裁剪后不能默认会有 modprobe 自动补齐遗漏模块。

早期模块必须与 uImage 中的内核匹配；正式 SquashFS 中的模块也必须与该内核匹配。不能拼接不同编译轮次或不同内核 ABI 的模块。

### 6.5 可以不进入早期环境的内容

在保持当前启动业务的前提下，可以从早期文件集合中排除完整网络服务、LuCI、包管理数据库、正式系统守护进程、LVM 用户态管理程序以及其他仅在正式系统接管后使用的业务文件。

正式 init、procd 和原版 mount_root 也无需因交接而提前复制：FAT init 对新根目录内这些程序的检查，可以在 SquashFS 挂载后完成；最终执行的 init 来自正式新根目录。

这些排除仅针对早期副本，不从正式 SquashFS 删除对应软件。

## 7．启动链如何衔接

优化后仍分为五个阶段：

1. **UBOOT 加载镜像。** 从 FAT 读取一个包含内核、DTB、精简 initramfs 的 uImage，启动内核。
2. **sd-init 建立最初环境。** 以 PID 1 运行，准备必要挂载和设备访问，加载 MMC/FAT，按 LABEL 识别并只读挂载 BOOT。
3. **FAT init 组装正式根目录。** 使用早期工具加载 loop 与 F2FS，读取对齐的 SquashFS 文件，定位 OVERLAY，挂载各层并生成 mount_root 包装脚本。
4. **交接。** 检查新根和控制台，安排 /boot、/rom、/overlay 的位置，正常清理早期虚拟文件系统，执行 switch_root。
5. **正式 OpenWrt 接管。** 正式 init 与 procd 启动服务，使用正式根目录中的工具和模块。

FAT 分区的 /boot/init，在 FAT 被挂到 Linux 的 /boot 后，访问路径是 /boot/boot/init。精简环境必须保持当前路径约定，避免误把 /boot/init 理解成 Linux 根目录下的同名路径。

### 7.1 不产生新的依赖倒挂

读取 SD、挂载 FAT、建立 loop 和挂载 SquashFS 所需的能力，必须在正式 SquashFS 可访问之前已经存在于内核或早期环境中。

正式业务软件可以留在 SquashFS；用于首次读取 SquashFS 的工具与驱动不能只留在 SquashFS。

### 7.2 upper 的处理规则不变

继续按全新空 upper 设计。需要的 mount_root 包装脚本在组装阶段生成；已经存在的对应文件按当前内容核对与更新策略处理，不能把旧 upper 中留下的脚本当成设计的一部分。

空 upper 是启动能力要求，不表示每次启动删除 upper。正常运行产生的配置仍然持久保存。

## 8．构建侧如何分离两个文件集合

### 8.1 首选概念：同一构建产物，派生两棵文件树

完整 OpenWrt 根目录继续用于生成正式 SquashFS。另建一个独立的早期目录，从相同构建结果中按功能清单选取文件，并补齐依赖，用于生成精简 initramfs。

这样可以复用同一套 ARM 工具链、同一套程序和同一批内核模块，避免再维护一套独立早期发行版。

不能为了缩小 initramfs，直接删除 root-kirkwood 中的文件后继续构建；那会同时影响正式 rootfs，并可能污染后续增量构建。

### 8.2 内嵌方式仍然沿用 initramfs

Linux 支持通过 INITRAMFS_SOURCE 指定早期文件来源，并将其归档嵌入内核。本文改变的是归档内容，不改变内核先运行早期用户态、再交接正式根目录的机制。[1]

OpenWrt 有自己的内核与 initramfs 构建编排。实施时必须确认最终规则真正使用了精简目录或对应归档，不能仅修改某个中间 .config 就认定已经接入成功。

概念上有两个候选接入点：使用 OpenWrt 对外部预制 CPIO 的构建入口，或增加明确的早期目录打包步骤。选型应以本项目固定版本的构建规则为准，本文暂不指定具体补丁、变量赋值或执行顺序。

### 8.3 需要解决的构建顺序

正式根目录中的程序和模块先要产生，才能从中选取精简早期集合；精简归档准备完成后，才能得到最终内嵌它的内核镜像。

如果采用分阶段构建，就必须明确每一阶段的输入、产物和重建边界，避免最终打包时又被默认完整根目录覆盖。一次性实现所有构建优化不是本专项的前提。

### 8.4 与两个配置片段的关系

现有两个最小片段描述目标设备、所需软件能力与 LIO 内核意图。精简早期环境主要新增的是“这些已构建文件中，哪些要提前进入 initramfs”的文件选择规则。

它不等于再手工写一份全部依赖配置，也不要求把正式系统的包配置缩成早期包集合。未来若需要增加打包规则，应独立管理，并清楚记录与两个片段及 sd-init 的关系。

## 9．内存收益应该如何理解

### 9.1 预计收益主要出现在哪里

较小的早期归档通常有利于减少 uImage 体积、加载与展开工作，以及正式根目录交接前的内存占用。具体收益取决于压缩方式、被删除文件以及内核构建结果，需要实际测量。

PogoV4 只有 128 MiB RAM，降低早期占用可以增加启动与故障诊断阶段的余量。但目前没有测量数据，不设定必须节省多少 MiB 或多少秒的承诺。

### 9.2 不能把镜像差额当作常驻内存收益

应区分：内核中的归档与初始化区、展开后的早期文件、已经加载的模块，以及正式运行中的进程和缓存。它们的生命周期不同。

此前日志中的“Freeing unused kernel image (initmem) memory: 13312K”发生在运行早期 shell 之前，不表示展开后的早期文件也全部释放。switch_root 清理旧根后，可以释放不再被引用的早期文件占用；模块和仍被引用的对象有各自的生命周期。[1]

因此，正式系统进入稳定运行后，完整与精简方案之间的内存差距可能小于启动阶段差距。不能用两个 uImage 的大小相减，也不能用 SquashFS 文件大小，推算最终可用内存增加值。

### 9.3 对 SD 寿命的关系

该优化主要针对镜像体积和早期资源占用。BOOT 只读、loop 只读和 SquashFS 只读的策略已经存在，精简 initramfs 并不会自动减少 F2FS 上的日志、配置或业务写入。

SD 延寿仍主要取决于正式系统的实际写入行为；本专项不将寿命提升作为已经得到证明的收益。

## 10．首轮实验的取舍

首轮建议只改变早期文件集合，保留当前 BusyBox、blkid、losetup、模块划分和两层启动脚本的业务接口。

| 方向 | 首轮处理 | 原因 |
|---|---|---|
| 独立精简目录 | 采用 | 不破坏正式根目录，便于核对差异 |
| 同源二进制与模块 | 采用 | 降低版本、架构和 ABI 混用风险 |
| 早期 shell 与基本诊断 | 保留 | 故障时仍能判断缺失环节 |
| 专用裁剪 BusyBox | 后续再评估 | 需要单独证明 applet 和功能选项完整 |
| 全部工具静态链接 | 后续再评估 | 需要比较总体体积及维护成本，不能假定一定更小 |
| MMC/FAT/loop 全部改内建 | 本专项首轮不做 | 会改变内核配置与对照条件 |
| LIO 内建改 kmod | 本专项不做 | 属于另一项包定义和模块管理工作 |
| 额外网络救援服务 | 首轮不增加 | 当前已具备串口诊断路径 |

“最小”在这里表示满足当前启动和基本诊断所需的合理最小集合，不追求以牺牲可维护性换取最后少量字节。

## 11．未来验证如何安排

### 11.1 对照条件

保留当前完整 initramfs 镜像作为对照。精简方案尽量使用相同源码、内核配置、正式 SquashFS、FAT init、SD 卡和测试条件，只改变早期文件集合及其打包。

嵌入归档改变后，uImage 校验值自然会变化；比较重点是功能和配置边界一致，而不是要求整个内核镜像逐字节相同。

### 11.2 功能验收

| 阶段 | 需要证明的结果 |
|---|---|
| 最初入口 | sd-init 能作为 PID 1 运行，串口可用 |
| 设备识别 | 按约定找到唯一 BOOT 和 OVERLAY，不依赖固定 Linux 分区号 |
| 文件读取 | FAT 只读；对齐的 SquashFS 文件可通过只读 loop 挂载 |
| 根目录组装 | 全新空 upper 能形成可写 overlay 根目录 |
| 包装脚本 | 正确处理当前 preinit 实际传入的 start 参数，并正确完成 done 检查 |
| 根目录交接 | switch_root 成功，PID 1 最终为 procd |
| 挂载结果 | /boot、/rom、/overlay 与根目录符合设计；虚拟文件系统无重复叠加 |
| 重启 | 已有 upper 可重复启动，不靠上一次 RAM 环境残留 |
| 正式系统 | 所需服务和业务能力与对照方案一致；LIO 另做实际 LUN 验证 |

### 11.3 缺失依赖和失败路径

重点覆盖：找不到 SD 分区、LABEL 不匹配或重复、FAT init 不存在或不可解析、根镜像缺失或未对齐、SquashFS 损坏、F2FS 挂载失败，以及工具、动态库或模块缺失。

失败时应输出可定位阶段的错误，保持 PID 1 和串口修复入口。不能通过自动格式化 OVERLAY 或删除 upper 来掩盖启动失败。重复执行检查时也不应叠加挂载或覆盖已有 loop 后端。

### 11.4 收益测量

记录三组指标：镜像与早期归档体积；从早期入口到根目录交接各阶段的耗时和内存；正式服务稳定后的内存状态。

启动阶段的若干采样点只能说明这些时刻的占用，不应自动当作完整峰值。对两种方案采用相同采样方式、多次启动，并说明测量边界。

同时记录故障 shell 中的可用内存和诊断工具是否足够。不能只测正常路径就删除所有失败处理工具。

## 12．实验产物和恢复边界

未来实施时，至少保留精简文件清单、依赖核对结果、构建来源信息、最终 uImage、配套正式 SquashFS，以及正常与失败路径的测试记录。

仍需保留当前完整 initramfs 的可工作镜像。实验失败时，可以恢复该镜像和兼容的 FAT init，不应要求重新格式化数据分区。实验期间如果另外改变了 upper 或业务配置，应单独记录，不能把恢复内核镜像等同于撤销所有数据变更。

具体清单格式、构建接入点和发布文件命名，留到实施阶段确定。本文不引入新的运行时版本选择系统。

## 13．后续实施前需要确定的问题

1. 精简目录如何从同一次 OpenWrt 构建产物中生成，并可重复得到相同的功能集合？
2. 如何自动收集目标程序的动态库闭包、链接目标及模块依赖，同时保留当前脚本的装载逻辑？
3. 固定版本 OpenWrt 的哪个构建入口能够可靠使用精简归档，且不影响正式 SquashFS？
4. 两层脚本修改后，怎样检查其新需求仍处于精简环境提供的能力范围内？
5. 实测收益是否足以承担额外的打包规则与回归维护成本？

在这些问题完成实现和验证之前，完整 initramfs 继续作为已知可工作的基线。
